# Phase 2i.2 mobile hosting decision

Decision record, 22 November 2026. Keep development local at zero incremental hosting cost. Pay for a persistent test environment when the team needs an always-on HTTPS origin for shared iOS/Android builds, real push delivery and recovery drills. The managed alternatives and acceptance checklist from Phase 2i.1 follow this revision.

**A. Disposable online testing.** Oracle ARM is the lowest nominal cost ($0) if capacity, artifact verification and synthetic data suffice. For the current verified x86 build, prefer a short-lived CX23 rehearsal. At €0.0088/hour compute, 48 hours is about €0.42 plus IPv4, tax and any retained storage. Use an existing delegated subdomain and disposable fixtures. Destroy resources after evidence collection with owner approval. Free preview services cannot verify the entire production topology.

**B. Persistent staging.** Budget €5.49 compute + approximately €0.50 public IPv4 monthly, plus $5 for a separate backup account's first 250 GiB of Spaces Standard including 1 TiB of outbound transfer. Using a planning conversion of $1.10/€, that is about **$12/month** with an existing domain. Budget another $1–2/month amortized for a new domain if needed. Use free certificate issuance and existing external checks only if their quotas suffice.

**C. Limited initial production.** Separate CX33, IP and separate backup account/bucket at the same assumptions: (€8.49 + €0.50) × 1.10 + $5 = **about $15/month**, or $16–17 with a new domain. Keeping staging online adds its own budget. These estimates assume included disk and transfer, no paid support, volunteer on-call and small backup volumes. Quote taxes, currency, volume growth, WAL transfer, monitoring subscription and emergency replacement capacity before purchase. A single host loses the API, scheduler, quotas and primary database together. Require measured recovery and an owner willing to operate PostgreSQL before admitting real users. Choose managed PostgreSQL if staffing or recovery evidence is inadequate.

## Mobile build configuration

| Environment | Expo public API base | Server and device policy |
|---|---|---|
| Development | Developer LAN address and FastAPI port for a physical phone. Android emulator can use 10.0.2.2, iOS simulator can use localhost. | Dedicated development database and keys. Allow LAN binding only on a trusted private development network. Keep HTTP exceptions confined to development builds. |
| Staging | Explicit staging HTTPS origin in the staging EAS build/update environment. | Production runtime policy, dedicated PostgreSQL, Redis, V2 session keys, Expo credentials and test accounts. Verify compiled origin on both platforms. |
| Production | Explicit production HTTPS origin in the production EAS build/update environment. | Production-only service identities and secrets, strict session settings, private stores and separate worker. Gate release on an HTTPS origin allowlist and an environment-matched update channel. |

The mobile client reads EXPO_PUBLIC_API_URL and has a local fallback and 15-second request timeout. Omission in a distributed build can direct requests to the device itself. Treat every Expo public variable as readable by anyone. Ship only the API origin here. Keep DB URLs, limiter keys, JWT keys, refresh receipt keys, push provider credentials and admin credentials server-side. Consumer traffic is native. Preserve GET /privacy/account-deletion; publish a reviewed externally reachable privacy policy and functioning verified deletion-request channel before store submission. A restricted browser admin dashboard remains a separate project.

## Single-host deployment adaptations and acceptance

1. Allocate isolated Ubuntu 24.04 x86 hosts per environment. Adapt deploy/Caddyfile.example to each real API domain. Restrict ingress to HTTPS and required certificate HTTP challenge/redirect, with administration restricted to trusted sources. Bind Uvicorn to loopback and trust only the local proxy. No public database or limiter ports.
2. Configure PostgreSQL durable disk, local-only access, authenticated separate API/worker/migrator roles, pg_hba rules and verified TLS when using TCP. Use a certificate matching the chosen local DNS name. Test private connection identity before migrations. Use deploy/redis.conf.example with protected Unix socket, API-only group, persisted state and noeviction. Alert on memory pressure and limiter errors.
3. Install separate API/worker units and secret files using the inventory below. Maintain V2 keys across restarts. Keep JWT material out of the worker. Set explicit memory/CPU and connection budgets after measuring peak Argon2 concurrency, long forecasts, backup activity and queue processing together. Reserve memory for PostgreSQL and the OS. Bound logs, monitor disk/WAL growth and leave room for restore operations.
4. Use one approved migrator after backup verification, before sending traffic. Test graceful drain, /ready recovery, scheduler restart, stale heartbeat and delivery reconciliation after interrupted sends. Schedule security updates, rehearse kernel reboots and verify external uptime and queue-age paging while the host is down.
5. Archive encrypted base backups and continuous WAL off-host using restricted writer credentials and separately recoverable decryption keys. Protect retained copies against host credential compromise. Apply the retention, timed restore, deletion reconciliation and recovery gates below. A snapshot of the primary disk cannot satisfy these gates alone.
6. Measure Egypt-to-candidate-region DNS, TLS and p50/p95 end-to-end timings over cellular and Wi-Fi, including cold launch, dashboard, large forecast and concurrent logins. Record payload bytes, timeouts and peak pool usage against the existing 15-second client budget. Do not guess regional latency. Use bounded existing endpoints and pagination where available. Honor 429 Retry-After and back off on 503; use single-flight refresh and the persisted idempotency key within the existing recovery window. Show offline state, avoid automatic financial-write replay and never treat a timed-out payment mutation as confirmed.
7. Before provisioning, owner approves budget including simultaneous environments, region/residency, DNS, operator and backup custody, recovery targets, acceptable outage and who responds to alerts. Require Windows smoke, staging mobile/real push tests, Linux/Caddy service validation, load tests, isolated restore and deletion drills before release. Every architecture and cost here is a proposal.

## Phase 2i.3 decision and Linux evidence gate

Stay local until a shared HTTPS origin is necessary for physical-device testing. Temporary CX23, persistent CX23 and separate CX33 remain successive candidates subject to approval. Neither sizing nor recovery time has been measured on these hosts. The consumer app uses the API directly; the future restricted admin origin has its own [design and acceptance plan](admin-dashboard-plan.md).

On an approved disposable Ubuntu host, substitute environment-specific paths and hostnames in copies of the examples. Run `caddy validate --config <rendered-Caddyfile> --adapter caddyfile` and `systemd-analyze verify <rendered-api.service> <rendered-worker.service>`. Install the hashed x86 lock and verify the artifact and migration head. Record service users and socket permissions, public listener inventory, rejected remote DB/Redis connections, unauthenticated admin denial, API readiness under dependency loss, heartbeat after worker restart, alert delivery and elapsed isolated restore time. Verify role-denied queries, worker exclusion from API secrets and restore/deletion reconciliation before enabling delivery. Capture redacted evidence on the actual Linux build. These gates are pending.

The tradeoff is one host failure domain and operator responsibility for Redis persistence, patching and recovery. If production is expected to use multiple API hosts, rehearse managed Valkey from the outset. A socket on each host would split security quotas.

1. Owner approves provider/region, ceiling, residency review, availability tier, proposed RPO/RTO, named SRE/DBA/privacy/mobile owners and migration authority. Capture provider confirmation of private DNS, CA, PITR window and cost. Compare latency from Cairo on cellular and Wi-Fi.
2. Infrastructure creates staging-only network and identities. Publish a staging DNS entry to the HTTPS edge, verify automatic renewal, firewall all other services. Set MFA and prepare break-glass access. Create separate secret scopes and roles. Validate Redis and PostgreSQL from actual API and worker networks.
3. Build reviewed SHA on clean Linux x86_64, patched CPython 3.12. Install requirements-linux-py312.lock with pip --require-hashes --only-binary=:all:, run pip check and separate pip-audit, record digest. Package alembic.ini and revisions. Validate actual Caddy and systemd versions using caddy validate and systemd-analyze verify. Set consistent checkout working directory.
4. DBA verifies staging target and role, reviews alembic heads/current/history, obtains encrypted restore point and restores a disposable copy. Only with separate persistent migration approval run alembic upgrade head once using migration-only credentials. Confirm single expected head 2f3a00000001 and core constraints. Never run release DDL in API or worker startup.
5. Start API via reviewed unit (uvicorn app.main:app on loopback behind Caddy). Gate traffic on /ready. Start separate python -m app.commands.notification_worker after tracking configured. It claims due work, retries/queries receipts and writes DB heartbeat. Validate supervision and graceful stop before sending to staging devices.
6. Jomana points a development build's EXPO_PUBLIC_API_URL to the actual staging HTTPS origin. Record mobile SHA, platform and build. Test registration, V2 login, restart/refresh, logout/401, cross-user isolation, financial profile, plan/down payment, pay/undo and dashboard/forecast/affordability reconciliation. Test deletion with password, session revocation and reminder suppression. Verify private notification copy, permission denial, tap routing and actual receipts on both platforms.
7. Test dependency outage/readiness, failed push recovery and alerts. Pause traffic and worker on bad rollout. Return to previous immutable artifact only if compatible with migrated schema. Otherwise isolate, review forward fix or approved restore, reconcile deletions, and repeat smoke gates. Keep synthetic logs and evidence in the release record.

## Operator acceptance and recovery

SRE assigns named primary/backup and acknowledgement/escalation windows. From outside, probe HTTPS /health each minute and verify certificate lifetime. From trusted ingress probe /ready for DB SELECT, exact migration head and Redis PING; consecutive failures remove traffic and page operators. A live process can be unready. Alert separately on DB connections, Redis memory/evictions, worker heartbeat age beyond configured threshold, sustained queue age, rejected deliveries, 5xx rate and unusual 401/429 bursts against baseline. Inject each failure once and record alarm delivery, acknowledgement and recovery time. Restrict diagnostic APIs to MFA-verified staff. Keep counts, timestamps and safe error classes. Suppress headers, URLs containing query values, bodies, email, amounts, push payloads and tokens across edge, provider and application logs. Propose 14-day staging operational log expiry with restricted access; separate admin audit retention requires privacy approval.

DBA requires daily encrypted backups plus continuous WAL/PITR, isolated backup access, encryption key recovery, age/failure alarms and at most 30-day retention. Daily snapshots alone cannot meet a 15-minute RPO. On each candidate verify the paid tier's actual recovery-point lag and measure restoration into an isolated target with API/worker egress disabled. Seed timestamped synthetic changes and a deletion, recover to a chosen point and measure data loss and elapsed time through reconciliation and application checks. Keep the service isolated if deletions cannot be established. Repeat quarterly and after material changes. Four hours is plausible for a small DB with tested automation and personnel: VPS adds host/config rebuild time, App Platform adds component redeploy/network setup, Render also requires a proven compatible limiter. None offers an end-to-end guarantee at the stated floor. A region-wide recovery commitment would require separately priced replicas, backups and drills. Redis recovery must retain or conservatively handle quota loss; do not bypass limits during outage.

## Decision checklist

- Ready now: versioned API/worker, deployment examples, Mac regression baseline, documented migrations and smoke contracts.
- Implementation required after provider choice: actual IAM/grants, service-specific secrets, Linux build and resource limits, private admin edge, log filters, alert routing and backup automation.
- Owner/provider gates: cost and region, named operators, domain control, billing, private endpoints, recovery tier, backup/deletion and support policy.
- Linux gates: hash-locked build, units, Caddy, socket ownership, CA trust, load and shutdown tests.
- Staging gates: controlled release/rollback, real probes, quotas, private DNS failover, restores, alerts and incident drills.
- Mobile gates: Jomana's Windows acceptance, staging URL, recorded V2 build, English/Arabic RTL, Android/iOS finance, deletion and push tests.
- Admin: CLI provisioning, existing MFA-protected operations, exact lookup and redacted diagnostics can be rehearsed without UI. Exercise revocation, denials, audit review and exceptional target-bound support grants with alerts before enabling them. A browser UI is required for a polished interactive operator workflow only. Develop it in parallel under a distinct origin and access policy.
- Production approval: separate resources, verified backup/restore, privacy/deletion channel, store disclosures, internal distribution and final owner sign-off before promotion. No provisioning or deployment evidence in this phase.
