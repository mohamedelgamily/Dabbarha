# v1.0 archival conversation storage policy

AI chat is removed from the v1.0 application. The runtime no longer imports or
maps conversation models, loads messages, retrieves documentation, initializes
providers, authorizes tools or accepts `/chat` requests. The current application
ORM metadata contains only `users` and `obligations`.

## Applied history and existing data

Both existing revisions are preserved byte-for-byte:

- `b3ce2a2bd889_create_users_and_obligations_tables.py`
- `17d4d0e39961_add_conversation_tables.py`

No retirement revision was added and no existing database was migrated. Existing
`conversations` and `conversation_messages` tables, rows, foreign keys and indexes
remain. A fresh database that replays the existing revision chain will also have
these unused tables. This is intentional history compatibility, not an AI feature.

Removing ORM metadata must not turn autogeneration into accidental data deletion.
`app/db/migration_policy.py`, wired into both Alembic environment paths, skips only
reflected, metadata-absent `conversations` and `conversation_messages` tables during
autogeneration. Other tables and schema changes are still compared. It neither
executes a drop nor prevents a separately authored migration from running.

Do not run an old downgrade to retire the feature: that would drop these tables.
Do not accept autogenerated or manual destructive DDL without reviewing retention
and an approved backup/restore plan. This release does not make ORM `create_all`
a migration mechanism for existing databases.

Historical obligations with `source=chatbot_entry` remain valid financial records.
The database check, API input compatibility and response source values are retained.
No records are relabeled or deleted, and this string does not activate chat.

## Separately approved future retirement

1. Agree retention, privacy, export and deletion requirements and a retirement date.
   Confirm no deployed clients, older backend versions, reports or support jobs use
   the archived tables. New v1.0 app code must not depend on them.
2. Identify each environment and applied revision, database engine, current row
   counts, foreign keys/indexes and authorized data owners. Inventory without
   exposing private message contents in logs or migration reports.
3. Take an access-controlled encrypted backup/export where retention requires it;
   verify restoration on a disposable database. Define how backup copies expire.
4. Design a new forward revision after the existing head. If deletion is approved,
   drop the child table/indexes before the parent table; choose engine-specific
   lock/transaction and deployment maintenance procedures. Do not rewrite history.
5. Review rollback honestly: recreating empty tables cannot restore deleted rows.
   Recovery depends on the verified retained backup and an approved restore plan.
6. Test on disposable copies for the selected production engine, then obtain
   explicit approval for target-environment execution. Remove the narrow autogenerate
   exclusion only as part of this separately reviewed retirement.

Phase 2b.2 tests use in-memory SQLite, replay the retained revisions, verify
registration/login/profile/obligation CRUD/forecast/dashboard/affordability and
cross-user denial with archival rows present, and run real Alembic autogenerate
checking. They do not access or mutate an existing local or production database.

## Residual privacy limitation

Archived messages still exist in databases and backups; removal of the API is not
data erasure or encryption. Existing physical foreign-key behavior and database
privileges/backup policies are unchanged. Storage access and retention need their
own operational review. This release has no admin or conversation-export endpoint.
