# Phase 2g.1 Backend Integration Review

## Scope and result

Reviewed the mobile-facing routes and schemas for registration, authentication, profile, device sessions, account deletion, obligations, installment schedules, payment occurrences, dashboard, forecast, affordability and notifications. Reviewed admin MFA/operations/support boundaries, notification delivery state, migrations and existing backend test coverage. No frontend source, real environment file, persistent database, or production service was changed or accessed by this review.

A focused integration regression exposed one cross-endpoint inconsistency: after an occurrence was marked paid, payment history and reminder suppression reflected the paid state, while dashboard, forecast and affordability still counted that scheduled payment as projected. The API paths now attach persisted paid occurrences to their owning obligations for the requested date window; forecast consumers omit paid regular occurrences while retaining the persisted schedule and legacy monthly calculation rules. Undo restores the projected amount. The complete mobile journey regression exercises registration through account deletion and verifies those endpoints against the same SQLite data.

## Data and ownership findings

- Every financial route uses the authenticated user ID in its database predicate. Child installment reads first confirm that the parent obligation belongs to that user. Occurrence mutations bind occurrence, obligation and user IDs. Account deletion derives the account exclusively from the authenticated principal and requires the current password plus explicit confirmation.
- New installment plans store exact cent-rounded schedule rows. `purchase_price` remains authoritative only for explicitly opted-in plans; `total_amount` remains a compatibility snapshot. Legacy obligations retain their previous recurring monthly formula. Forecast, dashboard and affordability consume exact rows for plans and legacy monthly amounts for legacy obligations.
- Paid regular occurrences now reduce projected remaining installment totals in dashboard, forecast and existing-obligation affordability inputs. A paid down payment is excluded using the established down-payment state. Mark-paid is the user's declaration, not bank verification. Undo is audited and does not resend already expired reminder offsets.
- Payment-occurrence reads can materialize rows, and notification preferences may lazily create defaults. These endpoints therefore have narrowly scoped persistence effects despite being HTTP GETs; clients should treat reads as safe to repeat, while the backend enforces unique occurrence/deduplication keys.
- Financial response totals are decimal strings with two-place monetary precision. Dates are ISO `YYYY-MM-DD`; date-times are ISO timestamps; session expiries are Unix seconds. Currency is an ISO-like three-letter code chosen by the user, defaulting to `EGP`.

## Security and integration findings

- v2 access JWTs are short lived and tied to a durable session. Refresh tokens are opaque, rotated, stored by digest, and recoverable only through the bounded encrypted receipt protocol. Mobile refresh must be single-flight and persist the retry key before sending. Legacy login remains a separate compatibility flow and does not issue a refresh token.
- Session, Redis, database, and encryption configuration fail closed on required protected paths. Production rate limits require shared private Redis. Do not put forwarded-IP headers, bearer tokens, refresh credentials, TOTP codes, push tokens, database URLs, or encryption keys in telemetry.
- Push tokens are encrypted at rest and bound to user/session metadata. Backend verification exercises queue/worker state and provider-adapter behavior, but does not verify APNs/FCM credentials, Expo project configuration, OS permissions, deep links on device, or delivery to a real phone.
- Admin routes are a distinct, default-off browser-dashboard API surface. Ordinary users and legacy tokens cannot access it. Operational admins cannot inspect financial records. Superadmin support reads require a specific time-limited grant and fresh single-use TOTP per read. No browser admin UI is included.
- Account deletion cascades user-linked financial, session, notification and conversation records. The app reports success only after commit. The public deletion information page does not receive external requests. Backup expiration/reconciliation is a deployment control, not code verified by local tests.
- Migration tests use disposable SQLite and PostgreSQL databases. Local migration success does not authorize or prove production migration safety; production migration execution, backup validation and rollback rehearsal remain release tasks.
