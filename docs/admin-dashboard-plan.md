# Restricted administrator dashboard proposal

Phase 2i.3 route audit at backend 46812c0. This was the pre-implementation design. The browser application and session adapter now live in admin-dashboard/. Deployment, operator ingress and production audit operations remain pending. Ordinary mobile sessions continue to use their existing origin and contracts.

## Capability matrix

Paths below are mounted in app/main.py. The handlers are in app/api/routes/sessions.py, admin.py and admin_support.py. Roles are enforced again by the API on requests. Navigation visibility is only a usability control.

| Capability | Existing API or operator control | Browser behavior and gap |
|---|---|---|
| Sign-in and MFA | POST /auth/sessions, POST /admin/auth/step-up, GET /admin/auth/me | Password establishes durable v2 session. Six-digit TOTP establishes session-bound admin bearer (default five minutes). Verify identity before displaying operations. Disabled API returns 404. No admin registration. |
| Session lifecycle | POST /auth/refresh, POST /auth/logout, GET /auth/sessions, POST /auth/sessions/{sid}/revoke | Serialize refresh per session, use existing retry-key/receipt rules. Logout upstream with exactly one credential. Session list and password-confirmed revocation belong to the current account. No cross-account revocation, suspension or admin account deletion API. |
| Overview and worker | GET /admin/ops/overview, GET /admin/ops/health | Both roles. Window 1–30 days. Refreshed sessions are an activity proxy. Unavailable deletion counts stay unknown. Show heartbeat stale/unknown and dependency failures. Public GET /health and GET /ready serve infrastructure probes. External alerting remains operational work. |
| Exact lookup and sessions | GET /admin/users/lookup, GET /admin/users/{user_id}/sessions | Exactly one ID or email. Offset pagination of sessions, limit at most 100. Read-only status, timestamps and device metadata. No account directory. |
| Delivery inspection | GET /admin/notifications/deliveries, GET /admin/users/{user_id}/deliveries | Bounded state filter, after_id and limit up to 100. Follow next_cursor on demand. Only normalized error categories and lifecycle metadata. No resend or queue-control API. |
| Grant administration | POST /admin/support-grants, GET /admin/support-grants/{grant_id}, POST /admin/support-grants/{grant_id}/approve and /revoke | Superadmin only. Exact grant ID; no grant directory or pending-approval inbox. Independent reviewer can receive the ID via the approved case channel. Inspect/revoke restricted to requester or approver. |
| Financial inspection | GET under /admin/support-grants/{grant_id}/users/{target_id}/ followed by financial-profile, obligations, obligations/{obligation_id}/installments or payment-statuses | Only original requesting session, active grant, matching scope and target. Fresh one-use X-Admin-TOTP on every read and page. Page limit 50, offset ceiling 1,000 on lists. No editing, export or impersonation. |
| Audit, role management and incidents | Backend writes audit events. Offline app.commands.admin_access supports provision and revoke. | No audit-history GET, role-management HTTP endpoint or incident command API. For MVP, reference the case and escalate to the authorized operator for audit review or role revocation. Never give the browser database access. |

If searchable audit history is required in-browser, obtain separate approval for a paginated, rate-limited, audited, role-restricted projection with deletion-safe references, bounded time range and no raw payloads. An approval inbox, third-party session kill, suspension, manual delivery retry and remote provisioning would also require separate backend and policy review. None is necessary to ship the read-only operations console. No financial support action changes the customer's account.

## Browser boundary and operating cost

Use a small server-rendered TypeScript application (for example Fastify with escaped templates), a same-origin backend-for-frontend (BFF), and minimal JavaScript. One supervised unprivileged service on loopback, one restricted HTTPS admin hostname behind Caddy, separate Unix identity and immutable release. Restrict ingress to approved operator network/VPN and guard direct /admin access on the API origin too. The BFF calls a fixed upstream route/method allowlist. Preserve trusted client-IP and rate-limit semantics through a reviewed proxy chain; strip caller forwarding headers. API authorization remains authoritative. Bind public mobile routes independently. Sharing a VPS avoids another instance charge if measured headroom permits; it shares the outage and compromise boundary. Separate the service onto its own host if isolation or load requires it. Budget DNS, access gateway and monitoring if existing allowances do not cover them.

Issue a random opaque __Host- cookie with Secure, HttpOnly, SameSite=Strict, Path=/ and no Domain. Proposed first version uses one BFF process with bounded in-memory session state, short idle/absolute deadlines and no persistent token cache. Restart requires sign-in. Store upstream credentials only server-side; discard password and codes immediately. Rotate handle on sign-in and privilege change. Clear state on logout/expiry and attempt upstream revocation on logout, eviction and graceful shutdown. Unexpected process death may leave an upstream session valid until revoked or expired; document own-device revocation and keep a short BFF lifetime. Do not report remote revocation as successful on an outage. No multi-replica rollout without a reviewed session strategy.

Check exact Origin and a session-bound CSRF token on every browser action, including sign-in, lookup, grant actions and sensitive page reads. Use POST forms for sensitive inputs and translate server-side to the upstream method. No generic proxy, cross-origin credentials, URL-based bearer, browser storage, third-party analytics or service worker. Enforce no-store, restrictive CSP (self-hosted assets, frame-ancestors none, object-src none, base-uri none, form-action self), HSTS, nosniff and same-origin referrer policy. Chromium requires a usable Origin on same-origin form POSTs. Suppress query strings, form data, cookies, headers and upstream bodies from logs across both hops. Clear sensitive content on logout, navigation and expiry; test browser history restoration. Display freshness and role from /admin/auth/me. Never silently renew MFA or prefetch support data.

## Implementation and acceptance sequence

The following module names refer to a proposed separate admin project. The implemented modules are server.mts, console.mts and layout.mts; the names in this original roadmap describe intended responsibilities.

| Phase and dependency | Proposed modules and existing API coverage | Automated gate | Manual acceptance |
|---|---|---|---|
| A. Browser foundation. Requires approved restricted origin and offline-enrolled synthetic admins | server/session.ts, server/upstream.ts, server/csrf.ts, views/sign-in and views/mfa. Use matrix sign-in, step-up, identity, refresh, logout and own-session APIs. New BFF only. | Test fixation, Origin/CSRF rejection including login, expired MFA, ordinary user denial, concurrent refresh, logout outage, cache/back navigation and upstream allowlist. | Both roles sign in; normal account never enters. Inspect browser storage, cookies and logs. Close expired sessions and verify upstream logout. |
| B. Overview. Requires A and worker telemetry | views/overview, views/health and server/operations.ts. Use both ops GETs. No API addition. | Test unknown metrics, stale heartbeat, Redis failure, bounded polling and Retry-After. | Operator distinguishes degraded dependency, unreachable console and missing worker signal; follow independent uptime alert. |
| C. User and delivery diagnostics. Requires A and approved privacy review | views/lookup, views/sessions, views/deliveries. Use exact lookup, session and both delivery GETs. No mutation or new API. | Test exact-input rule, pagination bounds, redaction, escaping untrusted display labels and no query logging. | Find one synthetic account, inspect a failed delivery, verify no raw provider data, account actions or persistent lookup history. |
| D. Case support and auditing. Requires A, case channel and audit reviewer | server/support.ts, views/grant and views/support-read. Use all grant and scoped read routes. Audit viewer deferred pending separate authorization. | Exercise independent and explicit self-approval, target/session mismatch, replay, expiry, scope denial, deleted account, role revocation and audit outage. | Request minimal scopes for one case, prefer second approver, show exceptional self-approval warning and evidence, request a new code for each page, revoke then confirm denial. |
| E. Release. Requires A–D, accepted Linux staging, synthetic users and incident owner | tests/browser, deploy/admin service and restricted Caddy example, operator runbook. Exercise all preceding APIs plus liveness/readiness. No new API. | Disposable DB/Redis backend suite, browser end-to-end tests with both roles, header/CSRF/cache checks, dependency audit, log scan and rollback rehearsal. | Verify public-edge denial and approved-network access, outage handling and alerts. Deploy pinned artifact to staging first; roll back to prior compatible artifact, invalidate BFF sessions, record owner sign-off before production. |

Show the grant target, opaque case reference, structured reason, selected scopes, approval type and expiry (15 minutes from request). Deny by default; a valid grant never extends an expired step-up. After login or a sensitive read, wait for a fresh authenticator code before the next sensitive operation. Clear financial results on context change. Surface 401 reauthentication, 403 access denial, 404 unavailable resource, 409 conflict, 422 correction, 429 delay and 503 temporary outage without showing raw errors. On suspected compromise, stop sensitive reads, revoke the grant or own session where authorized, contact the offline operator, review minimal audit evidence and follow the incident runbook. Do not retry a sensitive action automatically.
